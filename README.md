# OMP Manager

A local-first Windows desktop dashboard for independent Oh My Pi processes. Rust + Tauri, plain Svelte/TypeScript, and xterm.js. Herdr is not a dependency.

## Run

Prerequisites: Rust/MSVC with the Windows SDK, Node.js compatible with Vite 8, the system WebView2 runtime, and an installed `omp` on `PATH`. Windows 11 x64 is the exercised platform; other platforms are not verified.

```sh
npm ci --ignore-scripts
cargo install tauri-cli --version 2.12.0 --locked
cargo tauri dev
```

If OMP is not on `PATH`, set `OMP_BIN` to its executable path before launching the manager.

Build a standalone executable without downloading installer tooling:

```sh
cargo tauri build --no-bundle -- --locked
```

Output: `src-tauri/target/release/omp-manager.exe`. It embeds the UI; no Vite server is needed for the release executable.

## Use

- The app opens **The Manager** and starts its saved terminal by default. If it is not configured, its creation dialog opens instead; no working directory is invented.
- The global toolbar reads Settings, Previews, Import config, Agent setup, **Terminals** (Dashboard only), **The Manager**, **Previous projects**, **New instance**. **Browser**, **Terminal** and **Code diff** belong to a full-screen session's own toolbar.
- **Previous projects** opens a searchable dropdown of saved instances. Search by name, directory, or profile. Selecting one resumes/starts its saved OMP session and opens its full-screen terminal; an already-running session is only opened, never restarted. Multiple instances in the same directory remain separate entries.
- **New instance**: select/type a working directory, optional OMP profile, ordered YAML config overlays, and optional model/role override. Empty profile selects OMP's default profile; empty model leaves model resolution to OMP.
- **Reconnect** lists native saved sessions for the chosen project/profile. It does not attach to an externally running terminal process; the session must not already be open elsewhere.
- Clicking a tile's terminal preview (including **Start or reopen this OMP session**) resumes/starts that saved session and opens it full-screen. The tile's separate footer **Reopen** button still resumes it in place on the dashboard. Switching views does not stop other processes.
- **Stop** sends OMP's double-Ctrl+C exit sequence, waits for graceful shutdown, then force-stops the direct child if necessary. **Restart/Reopen** use the saved native session path.
- **Subagents** opens read-only previews; clicking a child opens its native rendered transcript. **View Plan** opens the session's plan file. **Plan** opens the plan agent on the left and the plan on the right, with headlines/full text and clickable heading navigation. It is available for sessions with unfinished todos, a native plan file, or a last saved plan. Completed todo lists hide the button. The plan agent interrupts the target's current turn before saving changes. **Every handoff requires a human confirmation in the plan agent's terminal**; for a stopped target the question explicitly offers to start it and hand off. Declining neither starts nor resumes the target. Confirmation applies only to the revision reviewed; a newer revision requires a new confirmation. Saved revisions appear in the split pane immediately (or on its next 3-second refresh), before handoff, rather than waiting for the worker's todo list to change. After an approved handoff, the pane follows the worker again when its live plan changes.
- **After plan handoff**, the open plan split view automatically switches to the receiving session's full-screen terminal (including The Manager), on the next instance update. Cancelled/failed handoffs, saving edits and restoring backups do not switch views. Reopening a plan view does not replay a previous successful handoff, and a handoff completed after you leave the view does not pull you back.
- **Plan backups**: each plan replacement first saves an immutable copy of the previous plan (including live todos) under `<app-config>/plan-changes/<session id>/backups/`. A backup failure prevents replacement. In the split pane, **Backups** lists the timestamped versions, previews their full text, and offers **Restore backup**. Restoring backs up the current version first and interrupts a running target, but never hands off or starts it; use the plan agent's separately confirmed handoff when ready. Saved revisions are tied to the target's native session, so switching to a different OMP conversation does not apply an old draft.
- **Previews Off** replaces the dashboard grid with Project → OMP → Subagent rows. Focused interactive terminals remain available. Choose Compact, Readable, or Large preview sizes in **Settings**; the size persists between launches.
- **Settings** (the cog to the left of Previews) selects the startup destination: The Manager, a chosen saved project, the latest non-Manager project opened full-screen, or **Dashboard**. Dashboard starts no terminals and does not open Manager setup, even if no Manager is configured. Its automatic-start checkbox is disabled while Dashboard is selected, retaining its value for other modes; it affects only app startup, not manual project opening. A missing chosen/latest project falls back to The Manager with a notice.
- **Show previous projects on dashboard** is off by default. Restored projects remain in the searchable dropdown and become dashboard-visible after you open them; new instances/workers appear immediately. Turning it on restores the all-project dashboard. Hiding rows never stops processes or removes history.
- Closing the desktop stops its managed processes. Definitions persist; only the configured startup target auto-starts on reopening when that setting is enabled. Remove deletes only the dashboard definition, not OMP history.
- **Terminal browsers**: OMP's native `browser.open` is routed to one isolated Chrome profile per saved terminal (`<app-config>/terminal-browsers/<sha256(instance id)>/profile`), launched only on first use. Cookies and logins stay in that profile; open tabs never do: every launch starts empty, so closing Chrome (or restarting the app) does not bring old tabs back. Terminals in the same repository and same-origin pages do not share cookies, storage, logins or named tabs. Provider sign-in windows and shell-launched browsers are unchanged. The browser is OMP's automation target and a real Chrome window (tabs, address bar, close) at once, so human and OMP input can overlap and conflict; there is no pause/take-control mode. Every tab in that Chrome belongs to the terminal's agent session: a tab you open by hand (or that a link opens) is attached automatically as `tab-1`, `tab-2`, … the next time the agent calls `browser.tabs()` or `browser.tab(name)`, so it can read and control it like any named tab (`browser.tabs()` shows each tab's `url` and `title`). `browser.open({name:'docs', app:{target:'<url or title substring>'}})` re-attaches an existing page under a name of your choice (omit `url`, which would navigate it). Closing a tab closes its page, and screenshots bring the attached tab to the front, so switching tabs by hand no longer makes the AI's own tab unusable. Each tab's CDP capability still exposes only its own page (and pages it opens); attachment is by the helper, never by a model-supplied endpoint. `app.path`, `app.cdp_url`, `app.relay` and `app.tern: true` overrides are rejected.
- **Settings → Show browser inside app** docks that Chrome window to a resizable pane on the right of the fullscreen terminal (terminal minimum 160 px, browser minimum 520 px; the window minimum width is 720 px). Switching terminals, Dashboard, minimizing, dialogs, the Previous projects popover, plans/subagent panels and divider drags hide the docked window without closing it. Turning the setting off moves the same running Chrome (same process and pages) to a normal external window; turning it on docks it again. **Headless browser** applies to the next browser launch only: a running browser keeps its mode, and headless browsers never create a pane or window. The pane has no additional app-owned header or close button; use Chrome's normal tab/window close controls. Closing Chrome leaves OMP running, and a later `browser.open` reuses the retained profile.
- **Browser** (full-session toolbar, not the global toolbar) shows that terminal's own browser next to its terminal, whatever the global *Show browser inside app* setting says: it starts the isolated Chrome headed if it is not running, or docks the already-running headed one (same process, same tabs; nothing is navigated). Other terminals and the global settings are unchanged. If the running browser is **headless**, the button asks before restarting it, because its open tabs are lost; declining changes nothing. Changing any Browser setting afterwards returns every terminal to the global preference (running browsers are not restarted). The button is disabled while the terminal is stopped; it never prompts a model.
- Tabs you open by hand in a browser started with the **Browser** button are visible to the agent on its first `browser.tabs()` / `browser.tab(name)`, even before it has called `browser.open` (they are attached as `tab-1`, `tab-2`, …). Asking for tabs never starts a browser.

### The Manager

- Click **The Manager**, select its working directory/profile/config, and create it. Subsequent clicks open/reopen the same native OMP session.
- Ask it to use **manage_sessions** to create dashboard workers, review their code/execution, inspect native plans, and handle native questions/approvals. Workers appear as ordinary dashboard instances, not OMP subagents.
- Existing user instances are independent until you click **Hand over to The Manager**. **Take back control** immediately revokes controller access without restarting the worker.
- **Needs you** shows an intervention reason. Open the worker and handle its native prompt, or press **Return to The Manager** after supplying the missing context. The Manager cannot clear its own human-intervention gate.
- **Settings → Show Manager tile** hides only the overview/tree row. The toolbar button, startup target, and session switcher remain available; notifications continue with the tile hidden or previews off.
- Stopping The Manager leaves workers running. Completion/decision notifications queue while it is offline and replay when it reconnects. Queues last only for the desktop app's lifetime; native OMP history remains durable.

Example: “Use manage_sessions to create a worker named API in C:/projects/api, ask it to review the failing build, and report when it finishes. Inspect its work before approving further execution.”

### Global config

- **Save as global config** previews non-secret native OMP settings from the selected instance (its `config.yml` plus ordered overlays) or from native default-profile config, then publishes an immutable snapshot under the app-config folder. **Import config** does the same from a `.yml`/`.yaml` file. Neither action writes to or modifies `.omp`.
- The active snapshot is the default for **new** instances, including Manager-created workers (`useGlobalConfig` defaults on; uncheck **Use global config** or pass `false` to opt out). It is placed before any explicit overlays and the `--model` override, so those win. Existing definitions, running sessions and older snapshots never change.
- Use a snapshot in another terminal with `omp --config '<saved path>'`; the dialog shows the exact command.
- Sanitized export/import keeps model roles and other registered non-secret settings. It omits credentials, headers/env maps, unknown settings, and `extensions`, `hooks`, `customTools`, `mcp`, `telemetry`, `auth`, and `shellPath`; excluded paths (never values) are listed. Model catalogs and authentication must exist locally. Requires Bun and the installed OMP SDK (`BUN_BIN`, `OMP_SDK_DIR`, `OMP_BIN` override discovery; the SDK and executable versions must match).

### Agent setup

- **Agent setup** is a full page: Scope → What to create → Describe → Tools (optional) → Review. Dashboard and Manager-origin setup offer **Global — default OMP profile** and **Just The Manager**. Opening setup from an ordinary full-screen project also offers **This repository**. Describe `AGENTS.md`, `RULES.md`, skills (`SKILL.md` plus a readable `SKILLS.md` catalog), reusable Python/Bash/TypeScript tools, and workflows. OMP profiles remain Global-only.
- **OMP plugin** is available in every scope and creates a native OMP extension package: `extensions/<name>/package.json` (`omp.extensions: ["index.ts"]`) plus `index.ts`, under Global's agent folder, the repository's `.omp`, or The Manager's `manager-setup` folder. Global and repository packages are found by native `extensions/` discovery; each valid Manager package is passed to The Manager (only) as an explicit `--extension` directory when it starts, so it never reaches workers or the global plugin registry. A malformed Manager package (bad `package.json`, missing or unloadable declared module, link leaving the folder) stops The Manager from starting with an explicit error instead of being skipped. Nothing is installed, linked or published; running sessions need a native reload or reopen. **OMP profile** is shown only under Global scope.
- Setup runs in a real, unowned OMP session in native plan mode. You review its native plan and choose a native execution option; target files are not written before approval, and The Manager cannot approve it. Completion is whatever the native session reports.
- Manager-only assets live in the app-owned `manager-setup` folder, loaded only into The Manager through a directory extension. `AGENTS.md`, `RULES.md` and `SKILLS.md` are re-read each Manager turn; new skills/tools/rules need a native reload or reopen. Nothing restarts The Manager automatically.
- Repository setup uses the nearest Git root (`.git` directory or worktree file), falling back to the project's working directory when no Git root exists. Its assets go into `<root>/.omp`; missing folders are not created before native approval. A setup job keeps its original project/root during retries and runs in an independent private session, not the project's current terminal.
- An unnamed repository Agents entry targets `.omp/AGENTS.md`; named entries target `.omp/agent-instructions/<name>/AGENTS.md` and are standalone, not automatically loaded or added to the Global/Manager Persona picker. An explicit `--append-system-prompt` can use them. Existing project terminals are not restarted/reloaded automatically; use/reopen OMP from the root for root-scoped rules/tools, since nested cwd or a nearer `.omp` can change discovery.
- **Open global .omp in VS Code**, **Open Manager folder in VS Code**, and the context-only **Open repository in VS Code** open the displayed folders with `Code.exe` directly (no shell). The repository action opens the root even before `.omp` exists; it does not create setup files.


### Code diff

- **Code diff** (full-session toolbar) opens a page for that session's project: a sidebar lists every changed file and a drop-down above it selects the baseline - **Since last commit** (`HEAD` against the working tree, including staged, unstaged and untracked files) or **Compared with master** (the branch tip against the working tree). The comparison branch is `master` when it exists, otherwise the repository's recorded default branch (remote HEAD or `init.defaultBranch`), otherwise `main`; the real name is shown and nothing is fetched. It works for stopped sessions and The Manager.
- The selected file opens in a bundled Monaco editor (the editor component of VS Code, loaded locally, no network): side-by-side diff with line numbers, the baseline side read-only and the working-tree side editable by typing and clicking. **Save** or Ctrl+S writes the file; nothing is autosaved and saving never stages anything. Saving preserves a file's BOM and LF/CRLF endings, and a deleted file can be recreated by editing its empty side.
- Saves compare the file's SHA-256 with the one loaded and refuse to overwrite a file an agent changed meanwhile (`diff_conflict`), keeping your typed text; **Reload from disk** discards it only after you confirm. Binary, non-UTF-8, mixed or lone-CR line-ending, links/junctions, submodules and files over 2 MiB are shown read-only with the reason. Only paths in the current comparison can be read or written, never `.git`, links or paths leaving the repository.
- Unsaved edits are guarded: switching file or baseline, Refresh, Git actions, Back to agent, Previous projects, The Manager, Agent setup, a new instance and closing the window all ask **Save / Discard / Cancel**. Git is only asked questions in the other two baselines (no shell, no textconv or external diff) and must be installed.
- The file list is a folder tree (folders collapse; collapse state lasts while the page is open) in every baseline. **Uncommitted changes** is the comparison option with index actions and mirrors VS Code's source control: **Staged Changes** (HEAD against the index, read-only) and **Changes** (index against the working tree, editable); a file staged and edited again appears in both. Row icons: **+** stages, **−** unstages, and the u-turn arrow reverts a Changes file (discards unstaged edits, or deletes an untracked file) after a confirmation; there are no bulk actions.
- **Commit** (message field under the drop-down; Ctrl+Enter also commits) commits only what is staged, runs the repository's hooks and reports Git's error text on failure. **Publish…** pushes the current branch (never forced; sets the upstream the first time), optionally after **Create new branch** (`git checkout -b <name>`), optionally followed by **Create pull request** (`gh pr create --fill`, which needs the GitHub CLI installed and signed in; its output or error is shown, and **Open pull request** opens the created link). Each step that already completed is listed if a later one fails.

### Git tree

- **Git tree**, next to **Refresh** in Code diff, opens a local Svelte Flow (`@xyflow/svelte 1.7.0`) commit graph. Cards show the commit subject, smaller author/date/hash metadata, and branch/tag badges. The graph includes local/remote branches, tags and detached HEAD, excludes stash-only history, and never fetches. It initially loads 300 commits; **Load more** extends the graph up to 5000.
- Click a commit to select it; Ctrl+click adds/removes selection. With two commits selected, **Compare selected** compares the older displayed commit to the newer one. Double-click a commit to see its changes against the first parent (or the empty tree for a root commit). Historical comparisons reuse the coloured file tree and Monaco diff editor but are read-only. **Back to Git tree** preserves graph selection and viewport.
- With one commit selected, **Revert** adds a commit undoing it and **Cherry-pick** applies it to the current branch. Both ask first; merge commits use the first parent. Start with a clean index/worktree: existing changes or a Git operation in progress are refused. Conflicts automatically abort this app's operation and show Git's error; an abort failure is reported rather than falsely claiming recovery.
- **Reset HEAD~1** asks before a mixed reset: HEAD moves to its first parent and the undone changes stay unstaged (added files become untracked). It does not perform a hard reset. **New branch** creates and switches to a named branch at the single selected commit, otherwise at HEAD.

### Terminal pane and Terminals page

- **Terminal** (full-session toolbar, next to **Browser**) toggles a pane on the right of the agent's terminal. It shares that slot with the browser: switching hides the other (a hidden browser's Chrome keeps running, the terminal's shell and AI commands keep running). Tabs: **0 · Terminal** is your own shell (closable; **Settings → Create a user terminal (Tab 0) when opening Terminal**, on by default, only applies when you click the Terminal button, never to an existing shell); **1 · History** lists every script the AI ran (timestamp, the AI's own description when it gave one, status, one-line preview; click a row for the exact full Bash/JavaScript/Python source and, when the command failed, the output it saved) with **Load older** for long histories; **2, 3, …** are live, read-only tabs for the AI's currently running commands (concurrent commands, backgrounded jobs and named Bash services included). A tab closes when its process actually ends; its record stays in History. Output shows the last 256 KiB.
- Every AI tab has one **Kill process** button. It stops that command, interrupts the agent like pressing Esc, and holds new Bash/Eval scripts until you send a new prompt in the agent's terminal (a prompt from The Manager or an extension does not release the hold; the pane says *Agent interrupted — send a new prompt to resume commands*). It is a human-only control: The Manager and models cannot call it.
- **Follow** (off by default, per view) switches to a command's tab when the AI starts one. **Settings → Automatically show terminal view for AI commands** (off by default) opens the pane of the session on screen when a command starts; it never changes session or page and never creates a user shell.
- On the Dashboard, **Terminals** (immediately left of **The Manager**) opens one page for every agent (including The Manager, plan agents and stopped agents): merged history labelled by agent, every live AI command and every existing user shell, and the same single **Kill process** button, which interrupts only the command's own agent. **Back to Dashboard** leaves it; nothing is stopped.
- History and live capture are recorded by the bundled bridge in each managed OMP process by wrapping OMP's real Bash/Eval tools (inside its approval layer; nothing is replaced) and stored under `<app-config>/terminal-sessions/<sha256(instance id)>/<sha256(session id)>/<execution id>/{script.txt,meta.json}`, plus `output.txt` for commands that failed (their final output, last 256 KiB); the output of commands that did not fail is not persisted. The agent can read the same history through the read-only `command_history` tool (`list` with optional status/query filters, `show` one command's script and saved output; current conversation only; an agent started before this version needs a restart to get the tool). Older conversations are imported read-only from their native journal (recorded call, description, timestamps and outcome, plus the result text of failed calls; calls nested inside an eval script that the journal never recorded cannot be reconstructed). Sessions started before this feature must be restarted to capture; if the installed OMP SDK cannot be found or is incompatible the pane says so instead of showing fake output. Your shell is the OS default shell (`%ComSpec%` on Windows) started in the project directory, owned by a Windows job object so closing the tab (or the app) ends its whole process tree.

## Data ownership

The manager stores launch definitions and their native session paths in Tauri's app-config directory (`instances.json`, identifier `dev.udvikler.omp-manager`). OMP owns sessions, chats, plans, configs, models, approvals, tools, and thinking visibility.
GUI startup/dashboard/browser preferences are stored in WebView localStorage under `omp-manager.settings`, separate from OMP config and global `browser.*` OMP settings. The existing Manager-tile preference is migrated; the Previews On/Off preference keeps its existing key.

The Rust reader consumes native OMP JSONL journals and their sibling artifact directories. It does not write OMP journals or copy them into a separate chat database. Main/subagent transcripts use `omp render` with the instance's working directory, profile, and config overlays. A bundled extension is loaded only into app-managed OMP processes; it reports exact native session identity, completion, and decisions, and exposes the Manager's controller tool. It is not installed into global OMP configuration.

Tile **working/idle** is an output-activity indicator, not an authoritative agent-lifecycle state. Tasks, plans, and child metadata reflect OMP's last persisted state; in-flight subagent status may lag until OMP persists an update. Streaming chat remains visible in the real terminal. PTY replay is bounded to 256 KiB; older history remains in OMP.

## Safety and dependencies

- No telemetry, updater, tray/autostart service, external dashboard server, worker-to-worker messaging, or model-management logic.
- The desktop broker listens only on `127.0.0.1` at an ephemeral port while the app runs. Each child authenticates with a private per-generation capability. No external network requests are made by the manager itself. OMP can use the providers, MCP servers, and extensions configured by the user.
- The Tauri permissions beyond `core:default` are `dialog:allow-open` and `core:window:allow-destroy` (to close the window after the unsaved-edits guard). The frontend loads only bundled assets in release mode; its CSP allows same-origin and `blob:` workers and `data:` fonts for the bundled Monaco editor, nothing remote. Windows DLL search excludes the current directory and `PATH` to avoid ConPTY DLL search-path hijacking.
- Rust PTYs use pinned `portable-pty 0.9.0` from WezTerm. UUID and Windows API crates were inspected from their published source manifests. The Tauri CLI is compiled from source rather than installed as a prebuilt npm CLI package.
- The headless terminal mirror uses pinned MIT `vt100 0.16.2`, inspected with its ordinary `itoa`, `unicode-width`, and `vte` dependencies; it has no build script or binary-download hook. Rust handles terminal cursor reports even when no preview exists.
- The diff editor uses pinned `monaco-editor 0.57.0` (installed with `--ignore-scripts`) and `sha2 0.10.9` for the save-conflict hash.
- `package-lock.json` and `src-tauri/Cargo.lock` are checked in. Use `npm ci --ignore-scripts` and Cargo's `--locked` option.
- None of the direct npm dependencies has an install hook. The lockfile includes optional macOS `fsevents`, which does declare one; `--ignore-scripts` disables it. Vite's development toolchain includes upstream prebuilt Rolldown/Lightning CSS platform binaries. These are build-time dependencies, not silently downloaded application executables.
- OMP extensions are executable user configuration, not a sandbox. The manager does not weaken OMP's approval or thinking configuration.

cargo test --manifest-path src-tauri/Cargo.toml --locked

Exercised on Windows: independent real OMP children; terminal handshake, input and response; preview-only startup; stop/restart and saved conversation continuity; application close/reopen with no autostart; native folder picker; native reconnect listing; plan viewing; subagent previews/full transcript; compact tree with no dashboard terminals; and responsive preview sizing.

Focus regression checked in the native desktop: with an OMP terminal running, open **New instance**, type in the Name field, resize the window, and let background updates arrive. The modal must retain keyboard focus. Creating the second instance must leave the first running. Terminal resizing never requests keyboard focus; the creation form uses a native modal dialog.

Rendering regression checked in the native desktop: type an unsent draft and leave the focused session open across background updates. The xterm screen, input focus, and draft must remain stable without same-size PTY resize requests. Real window resizing still updates rows/columns once per geometry change, including the 500-column limit; restarting the OMP process intentionally creates a new terminal.

Regression tests cover persisted launch definitions, native todo/plan/subagent decoding, append updates, truncation/replacement, partial UTF-8 records, and local-plan traversal rejection.

Controller verification used isolated native desktop projects and real OMP 18.8.7 sessions with the configured GPT-6.1-Sol: background worker creation without a mounted preview; completion notifications; native always-ask write approval; code/file review; pending-dialog handover without restart; human escalation/return; native plan review and execution using terminal keys; hidden-manager/tree notifications; and stopping/reopening The Manager without stopping workers. Unit checks cover capability rejection, stale/revoked decisions, subscriptions, ownership persistence, native answer validation, and headless cursor reports.

Config and setup verification used an isolated desktop: sanitized preview/save/import; defaults inherited by new instances and a Manager-created worker while running sessions kept their snapshot; explicit overlay precedence and opt-out; complete Global and Manager-only setups reviewed and approved in native plan mode with every file kind generated; native discovery and real execution of the generated Python/Bash/TypeScript tools; a running Manager applying a changed private instruction without restart; both VS Code windows; and narrow-window layout. Unit checks cover the sanitizer, immutable snapshots, creation-time freezing, setup request validation, replay protection, and plan-path correlation.

Controller authorization is not a filesystem sandbox: OMP's ordinary tools retain the user's configured access. Native explicit deny rules, disabled choices, and thinking visibility remain authoritative. Custom/plan overlays are controlled through their real terminal screen and keys, not fabricated approval APIs. Compatibility is grounded in OMP 18.8.7; incompatible native UI contracts surface errors rather than silently bypassing policy.

### Terminal browser implementation notes

- The docked window is Chrome's own top-level window positioned over the pane, not a `SetParent` child: a native probe showed cross-process child hosting painted Chrome and accepted page input but broke the address bar and browser shortcuts. Docking relies on a 40 ms Win32 reconcile loop (position, visibility, z-order). The pane is a placeholder; the real window can briefly lag behind very fast resizes or window drags.
- A per-app Bun helper (`omp-browser-service.mjs`, started lazily) owns the Chrome processes and a loopback scoped CDP proxy. Each named tab gets an unguessable `*.localhost` capability origin (Puppeteer discards URL paths); the proxy exposes only that tab, its frames/workers/opened pages and pages it creates, and blocks peer pages, browser-wide control and peer downloads. A guarded adapter (`omp-browser.mjs`) wraps OMP's live browser prelude callback; if OMP's internal shape changes it fails closed with `OMP Manager browser integration is incompatible with this OMP version`. Requires Bun, the installed OMP SDK and a Chromium (`PUPPETEER_EXECUTABLE_PATH` selects one).
- Browser allocation and explicit tab-close requests use the authenticated Manager bridge. The hub keeps reading an authenticated bridge connection however long it is idle (a regression test sleeps past the 10 s hello deadline); if a connection ever stops being read it is closed so the bridge reconnects instead of waiting for a reply that cannot come. URL reads, tab enumeration and automation validate the existing tab directly through its capability-scoped CDP discovery endpoint, then use OMP's native CDP implementation; they do not depend on a redundant controller-validation round-trip. Closed/revoked capabilities still fail explicitly and closed named tabs are removed from OMP's list. The native integration regressions require `OMP_SDK_DIR` and `PUPPETEER_EXECUTABLE_PATH` and cover controller reply loss, closing Chrome and asking the same OMP session to reopen it, and an app restart, with real Chrome/SDK operations. A relaunch waits for the previous Chrome process to exit, and opening a tab is bounded (20 s): an unresponsive browser is closed with an explicit error so the next `browser.open` starts fresh. The helper's lifecycle trace is written to `<app-config>/terminal-browsers/browser-service.log` (overwritten per helper start).
- Headless Chrome stays a Chrome process owned by the helper's Windows job object, so it is reaped if the desktop or helper dies. This is routing isolation, not an OS sandbox against arbitrary local code.
