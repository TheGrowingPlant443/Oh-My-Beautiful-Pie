# OMP Manager

A local-first desktop dashboard for independent Oh My Pi processes, with the existing Windows path and additive native Linux/macOS builds. Rust + Tauri, plain Svelte/TypeScript, and xterm.js. Herdr is not a dependency.

## Run

### Windows

Prerequisites: Rust/MSVC with the Windows SDK, Node.js compatible with Vite 8, the system WebView2 runtime, and an installed `omp` on `PATH`. Windows 11 x64 is the exercised platform; other platforms are not verified.

```sh
npm ci --ignore-scripts
cargo install tauri-cli --version 2.12.0 --locked
cargo tauri dev
```

If OMP is not on `PATH`, set `OMP_BIN` to its executable path before launching the manager.

Build a standalone executable without downloading installer tooling:

```sh
cargo tauri build --no-bundle -- --locked
```

Output: `src-tauri/target/release/omp-manager.exe`. It embeds the UI; no Vite server is needed for the release executable.

### macOS release downloads

The [GitHub releases](https://github.com/TheGrowingPlant443/Oh-My-Beautiful-Pie/releases) provide a native **Apple Silicon (arm64)** `.app` ZIP for **macOS 15 or later**. Extract the ZIP and move **OMP Manager.app** into Applications. This download does not require Nix; the Nix packages below are a separate installation path. Intel release downloads are not provided.

The app is ad-hoc signed, not Apple Developer ID signed or notarized. Gatekeeper may require approval in **System Settings → Privacy & Security** after the first launch attempt; managed Macs may prohibit it. Do not disable Gatekeeper globally.

Install **OMP 18.12.6**, its matching SDK, Bun and Node.js separately; these downloads embed the UI and bridge scripts, not those runtimes. Finder launch uses the same executable/SDK discovery described below. Optional parser, browser, container and local-knowledge features retain their documented prerequisites. Terminal launch with overrides is available through `/Applications/OMP Manager.app/Contents/MacOS/omp-manager`.

Maintainers: manually run **macOS app** in GitHub Actions on the release commit. It builds on a native Apple Silicon macOS 15 runner, materializes locked frontend/Cargo dependencies through Nix, compiles with the runner's native Rust/Apple toolchain, runs backend tests, checks the packaged CLI and system-library linkage, and uploads the arm64 ZIP. Attach the ZIP and its SHA-256 checksum to a release targeting that same commit. The workflow does not publish automatically, and its headless checks do not verify Finder interaction, Keychain prompts or container integration; releases remain previews until those are checked on a real Mac.

### Linux and macOS

The flake exposes native `x86_64-linux`, `aarch64-linux`, `x86_64-darwin` and `aarch64-darwin` packages. Build on the target OS/architecture (or use a matching Nix remote builder); Linux cannot runtime-test the macOS app. macOS builds, Finder launch, Keychain prompts and Podman-machine integration require verification on a real Mac; they are not claimed tested by a Linux build.

Prerequisites are a working Nix installation with `nix-command` and `flakes` enabled, a graphical user session, and an existing **OMP 18.12.6** executable. The app does not install or replace your OMP executable, model configuration, credentials or sessions. The first Nix build can download a substantial Rust/WebKit/Node closure and compile Rust dependencies; all npm dependency materialization and frontend compilation happen inside Nix derivations, not in your checkout.

From the repository root:

```sh
# Build the frontend and release Rust binary; no Tauri CLI or Vite server is needed.
nix build .#omp-manager

# Omit this when the matching omp is already discoverable.
export OMP_BIN="$HOME/.local/bin/omp"
./result/bin/omp-manager

# Equivalent build-and-run entry point:
nix run .
```

`packages.default` is `omp-manager`; `packages.frontend` contains the generated UI, and `packages.sdk` contains the pinned bridge SDK. The Rust package builds with `tauri/custom-protocol` so the UI, bridge modules, source-index scripts, scanner assets and SRS templates are embedded. Source filtering excludes `target`, `node_modules`, `dist`, worktrees and unrelated root files. Linux uses GTK 3/WebKitGTK 4.1 and bundled GIO/schema paths; macOS uses native WebKit/frameworks from the Nix stdenv's Apple SDK. This is a Nix package, not an AppImage, DMG, signed/notarized installer or cross-platform executable.

#### OMP executable and SDK

The package wrapper supplies Bun, Node.js, Git, the existing Tree-sitter Python environment, and an immutable **`@oh-my-pi/pi-coding-agent` 18.12.6** SDK. The SDK is built from `nix/omp-sdk/package.json` plus its integrity-pinned, hydrated `registry-lock.json`. Lifecycle scripts are disabled, including optional native/ONNX download hooks; no package is installed at app startup. The bridge consumes the SDK's source, not an SDK-installed replacement `omp`.

To build/use the SDK separately:

```sh
nix build .#sdk --out-link result-sdk
export OMP_SDK_DIR="$PWD/result-sdk/node_modules/@oh-my-pi/pi-coding-agent"
export OMP_BIN="$HOME/.local/bin/omp"
nix run .
```

Normally omit `OMP_SDK_DIR`: the packaged launcher and `nix develop` set its default to the pinned SDK. An explicit `OMP_SDK_DIR` wins and is exclusive: point it at the package directory containing `package.json`, `src/config/settings.ts` and `src/config/registry.ts`, **not** at the enclosing `node_modules`. The app checks the executable's `omp/<version>` against the SDK version and refuses a mismatch. When updating OMP, update the SDK version and its complete integrity-bearing registry lock together and recheck the bridge against that exact executable; changing only the manifest is insufficient.

For an unwrapped binary, discovery also covers Bun's existing global SDK (`BUN_INSTALL` or `~/.bun/install/global/node_modules/...`), `${XDG_DATA_HOME:-$HOME/.local/share}/omp-manager/sdk/node_modules/...`, `~/.local/share/omp-manager/sdk/node_modules/...`, macOS `~/Library/Application Support/omp-manager/sdk/node_modules/...`, and an SDK beside/in the resolved OMP installation. These are discovery locations, not instructions to run a non-Nix installer. `OMP_BIN` and `BUN_BIN` override executable discovery. Unix desktop launch also searches existing `~/.local/bin`, `~/.bun/bin`, `~/.nix-profile/bin`, `~/.cargo/bin` and conventional system locations after inherited `PATH`.

#### Desktop installation and development environment

```sh
# Persistent per-user application installation; no sudo:
nix profile add .#omp-manager
omp-manager
```

On Linux, the package includes `share/applications/omp-manager.desktop` with an absolute store-path launcher. If your desktop does not discover Nix profile desktop entries, after `nix build .#omp-manager` install the entry explicitly:

```sh
install -Dm644 result/share/applications/omp-manager.desktop \
  "$HOME/.local/share/applications/omp-manager.desktop"
```

Reinstall that entry after rebuilding/updating; keep the Nix profile installation or `result` GC root so the referenced store path remains live. Do not launch as root: the app needs your session bus, keyring and rootless container store.

On macOS the package also contains `result/Applications/OMP Manager.app`. The direct terminal command above is the primary smoke path. For Finder registration after building:

```sh
mkdir -p "$HOME/Applications"
ln -sfn "$PWD/result/Applications/OMP Manager.app" "$HOME/Applications/OMP Manager.app"
open "$HOME/Applications/OMP Manager.app"
```

Keep `result` or install the Nix profile to retain the store path. Finder does not inherit shell-local overrides; make the matching `omp` discoverable in a documented location, or launch from a terminal with `OMP_BIN`/`OMP_SDK_DIR` exported. The bundle is unsigned and unnotarized; organization/Gatekeeper policy may require local approval.

`nix develop` supplies the existing Rust/Node/Bun/parser development environment and native libraries, plus the pinned SDK. It does not mutate `node_modules`; use `nix build .#frontend` for a reproducible frontend build instead of installing npm dependencies outside Nix. The Windows workflow above is unchanged.

#### Native runtime prerequisites and platform differences

- **Linux Code quality:** uses an existing local Podman installation and the current user's native/rootless container store; there is no WSL and no app-created Linux VM. Install a missing CLI through Nix, for example `nix profile add --inputs-from . nixpkgs#podman`. A working host setup still needs subordinate UID/GID mappings, networking/storage helpers, and the appropriate cgroup delegation; installing a CLI does not configure these host services. Docker is an explicit alternative, never a silent fallback. Unsupported resource controllers are reported rather than treated as enforced limits.
- **macOS Code quality:** uses an existing Podman machine/connection or an existing Docker Desktop installation. Podman needs a real configured VM and its provider; merely adding its CLI is not enough. Nix can supply the CLI (`nix profile add --inputs-from . nixpkgs#podman`), but this flake does not install/configure a hypervisor, Podman VM or Docker Desktop. Those are separate host prerequisites. macOS has no WSL path.
- **Consent and limits:** Unix has no automatic runtime/Windows-feature installer. Starting configured quality services and pulling their pinned images is explicit. SonarQube needs approximately 5 GiB engine memory and Linux-kernel limits `vm.max_map_count >= 524288` and `fs.file-max >= 131072`; for macOS these are VM limits, not macOS host sysctls. The app's consented limit action uses the existing host authorization mechanism on Linux or the selected Podman machine on macOS; an unavailable action reports manual steps rather than pretending it succeeded.
- **Credentials:** Code quality tokens/database passwords use Linux Secret Service through `secret-tool` (the Nix package includes the libsecret client), macOS login Keychain through `/usr/bin/security`, or Windows Credential Manager on Windows. Linux still needs a running, unlocked Secret Service provider such as GNOME Keyring or KWallet and the user's D-Bus session. Nix does not replace or configure the host desktop/keyring. A missing/locked store is an actionable error, not a plaintext fallback.
- **Browser:** Win32 Chrome docking/embedded-window behavior remains Windows-only. Linux/macOS use external browser windows; they do not embed a foreign Chrome window in the terminal pane. A compatible browser/Chrome installation is separate from this package and may need `PUPPETEER_EXECUTABLE_PATH`.
- **Process containment:** Unix has no Windows Job Object equivalent that outlives the manager. Chrome and the Cognee UI run in their own session and are retired on normal exit, but if the manager is killed or crashes they keep running (a leftover Chrome blocks that terminal's profile; a leftover Next server keeps the Cognee UI port). Stop them yourself after a crash. A `--code-quality scan` that is interrupted can likewise leave its scanner container until `down`.
- **Cognee UI:** Linux and macOS start the frontend (Next.js 16.3.4 only) from an installed cognee-frontend with Node.js on `PATH`; the backend must already be running and is recognized only by its own venv interpreter and loopback listener. On macOS process discovery parses `ps` and `lsof`, so a home folder containing spaces can hide the backend. Nothing here downloads or installs the frontend or backend.
- **Keyring prompts:** Credential reads wait up to two minutes for an unlock prompt, and the first read happens during app start. Unlock the Secret Service/Keychain before launching.
- **Flake sources:** A flake only sees files tracked by git. After adding new files to a working tree, `git add` them before `nix build .#…`, or build with `path:.#…`.
- **macOS case sensitivity:** project and credential identities are case-sensitive on Unix, so one folder opened with different letter case on a default (case-insensitive) macOS volume is treated as two projects.
- **Independent tools:** Ponytail, optional flow tooling and standalone search/Searx services remain independent of OMP Manager. This package does not make them application features or mandatory setup dependencies.

#### Native Code quality CLI

The Unix executable can use the same real service, OS credential store, process lock and saved reports without opening a Tauri window. For an isolated native smoke run, use one persistent state directory and a free port; `9001` avoids an independent service already using `9000`:

```sh
nix build .#omp-manager
./result/bin/omp-manager --code-quality --help
./result/bin/omp-manager --code-quality up --port 9001 --state-dir /tmp/omp-quality
./result/bin/omp-manager --code-quality status --state-dir /tmp/omp-quality
./result/bin/omp-manager --code-quality scan /absolute/path/to/project --state-dir /tmp/omp-quality
./result/bin/omp-manager --code-quality down --state-dir /tmp/omp-quality
```

Keep the same `--state-dir` for every call; it is the app-config root and contains `code-quality/`. Without the flag, the CLI shares the normal GUI configuration/ownership root. `up` saves the port, so later commands can omit `--port`; `status`/`down` reject a different override. `up` and `scan` leave services running. `down` stops only app-owned quality resources, retains data/reports, and does not shut down the container engine or VM.

`up` explicitly consents to starting configured services/pulling images, never installing a Unix runtime. `scan` explicitly approves the detected recipe and uses the normal disposable snapshot; build-based recipes can execute project build code. Ambiguous build families or .NET entry points require a saved GUI selection first. Run it only on a project you trust. The one-hour service watchdog remains in effect. Linux Secret Service/macOS Keychain and native runtime prerequisites above still apply; “headless” does not mean an unlocked credential store is unnecessary.

The CLI writes allowlisted JSON to stdout and errors to stderr; secrets, logs, build arguments and finding messages are omitted from that JSON. Exit codes: `0` success, `1` infrastructure/incomplete run or unknown gate, `2` a completed scan with findings or a failed gate, `64` invalid arguments. A `2` is not a service startup failure and must not be reported as a clean scan.

## Use

- The app declares a dark color scheme so native dropdowns and other form controls match its dark interface even when the operating system uses a light theme.
- The app provisions **The Manager** and **The Architect** without a folder chooser, then opens/starts only the configured startup target (Manager by default). Missing definitions use the first available real project from folder history/saved projects, or separate deterministic app-managed temporary workspaces. Existing coordinator settings and conversations are preserved. A provisioning error stays visible with **Retry** and **Configure manually** actions.
- The global toolbar reads Settings, Previews, Import config, Agent setup, **Terminals** (on every page, with a count of agents waiting for an answer, glowing when an off-screen decision needs you), **The Architect**, **The Manager**, **Previous projects**, **New instance**. **Browser**, **Terminal** and **Code diff** belong to a full-screen session's own toolbar. The full-screen toolbar has no **Stop** button (use the dashboard tile or the tree); a stopped agent shows **Start / reopen**.
- **Previous projects** opens a searchable dropdown of saved instances. Search by name, directory, or profile. Selecting one resumes/starts its saved OMP session and opens its full-screen terminal; an already-running session is only opened, never restarted. **Settings → Always start a new session** (off by default) makes starting a stopped agent begin a fresh session instead of resuming; Restart, helper/plan agents and a session chosen with Reconnect are unaffected. Multiple instances in the same directory remain separate entries.
- The session switcher (the drop-down beside **Dashboard**) opens the chosen session and starts it when it is not running; a running session is only opened. A second drop-down, **Same repository · N**, appears beside it only while other agents are running or starting on the same project folder: other sessions on that folder and the Code diff / Git tree helper agents (subagents and plan agents are not listed). Choosing one opens it full-screen; a helper opens as a plain terminal and is never remembered as the latest project.
- **New instance**: select/type a working directory, optional OMP profile, ordered YAML config overlays, and optional model/role override. Empty profile selects OMP's default profile; empty model leaves model resolution to OMP.
- **Reconnect** lists native saved sessions for the chosen project/profile. It does not attach to an externally running terminal process; the session must not already be open elsewhere.
- Clicking a tile's terminal preview (including **Start or reopen this OMP session**) resumes/starts that saved session and opens it full-screen. The tile's separate footer **Reopen** button still resumes it in place on the dashboard. Switching views does not stop other processes.
- **Stop** sends OMP's double-Ctrl+C exit sequence, waits for graceful shutdown, then force-stops the direct child if necessary. **Restart/Reopen** use the saved native session path.
- **Subagents: N** opens OMP's own native **Agent Hub** (the SDK's agents roster overlay) on that agent's existing session. It replaces the former read-only transcript cards and shows no app-rendered transcript. The button focuses the existing session (a stopped session is resumed through the normal saved-session path, never started fresh), waits until its bridge and interactive terminal are ready, opens the hub once for that session generation and gives the terminal keyboard focus. It creates no session, submits no input, types no `/agents` and leaves the composer draft alone; it also works while the model is streaming. The hub is OMP's own, so navigation, an empty roster, reuse of an already open hub and dismissal are native (the app adds no close button). The count is informational only; the button is disabled while the session is starting or until its bridge reports a hub-capable host. Clicking a child in the tree row opens the same parent's hub (children are not deep-linked). The action is abandoned if you navigate away or the session restarts while it waits. Errors: `native_agent_hub_unavailable: Reopen this session with a compatible OMP version.` (session started before this feature, or an SDK without the hub; the terminal stays usable), `native_ui_busy` (another native dialog, such as a pending approval, currently owns the terminal surface: nothing is closed or queued over it) and `stale_generation` (the session restarted). **View Plan** opens the session's plan file. **Plan** opens the plan agent on the left and the plan on the right, with headlines/full text and clickable heading navigation. It is available for sessions with unfinished todos, a native plan file, or a last saved plan. Completed todo lists hide the button. The plan agent interrupts the target's current turn before saving changes. **Every handoff requires a human confirmation in the plan agent's terminal**; for a stopped target the question explicitly offers to start it and hand off. Declining neither starts nor resumes the target. Confirmation applies only to the revision reviewed; a newer revision requires a new confirmation. Saved revisions appear in the split pane immediately (or on its next 3-second refresh), before handoff, rather than waiting for the worker's todo list to change. After an approved handoff, the pane follows the worker again when its live plan changes.
- **After plan handoff**, the open plan split view automatically switches to the receiving session's full-screen terminal (including The Manager), on the next instance update. Cancelled/failed handoffs, saving edits and restoring backups do not switch views. Reopening a plan view does not replay a previous successful handoff, and a handoff completed after you leave the view does not pull you back.
- **Plan backups**: each plan replacement first saves an immutable copy of the previous plan (including live todos) under `<app-config>/plan-changes/<session id>/backups/`. A backup failure prevents replacement. In the split pane, **Backups** lists the timestamped versions, previews their full text, and offers **Restore backup**. Restoring backs up the current version first and interrupts a running target, but never hands off or starts it; use the plan agent's separately confirmed handoff when ready. Saved revisions are tied to the target's native session, so switching to a different OMP conversation does not apply an old draft.
- **Previews Off** replaces the dashboard grid with Project → OMP → Subagent rows. Focused interactive terminals remain available. Choose Compact, Readable, or Large preview sizes in **Settings**; the size persists between launches.
- **Settings** (the cog to the left of Previews) selects the startup destination: The Manager, The Architect, a chosen saved project, the latest ordinary project opened full-screen, or **Dashboard**. Dashboard and Auto-start off start no terminals; both coordinator definitions are still provisioned. The automatic-start checkbox is disabled for Dashboard, retaining its value for other modes; it affects only app startup, not manual project opening. A missing chosen/latest project falls back to The Manager with a notice.
- **Show previous projects on dashboard** is off by default. Restored projects remain in the searchable dropdown and become dashboard-visible after you open them; new instances/workers appear immediately. Turning it on restores the all-project dashboard. Hiding rows never stops processes or removes history.
- Closing the desktop stops its managed processes. Definitions persist; only the configured startup target auto-starts on reopening when that setting is enabled. Remove deletes only the dashboard definition, not OMP history.
- **Terminal browsers**: OMP's native `browser.open` is routed to one isolated Chrome profile per saved terminal (`<app-config>/terminal-browsers/<sha256(instance id)>/profile`), launched only on first use. Cookies and logins stay in that profile; open tabs never do: every launch starts empty, so closing Chrome (or restarting the app) does not bring old tabs back. Terminals in the same repository and same-origin pages do not share cookies, storage, logins or named tabs. Provider sign-in windows and shell-launched browsers are unchanged. The browser is OMP's automation target and a real Chrome window (tabs, address bar, close) at once, so human and OMP input can overlap and conflict; there is no pause/take-control mode. Every tab in that Chrome belongs to the terminal's agent session: a tab you open by hand (or that a link opens) is attached automatically as `tab-1`, `tab-2`, … the next time the agent calls `browser.tabs()` or `browser.tab(name)`, so it can read and control it like any named tab (`browser.tabs()` shows each tab's `url` and `title`). `browser.open({name:'docs', app:{target:'<url or title substring>'}})` re-attaches an existing page under a name of your choice (omit `url`, which would navigate it). Closing a tab closes its page, and screenshots bring the attached tab to the front, so switching tabs by hand no longer makes the AI's own tab unusable. Each tab's CDP capability still exposes only its own page (and pages it opens); attachment is by the helper, never by a model-supplied endpoint. `app.path`, `app.cdp_url`, `app.relay` and `app.tern: true` overrides are rejected.
- **Settings → Show browser inside app** docks that Chrome window to a resizable pane on the right of the fullscreen terminal (terminal minimum 160 px, browser minimum 520 px; the window minimum width is 720 px). Switching terminals, Dashboard, minimizing, dialogs, the Previous projects popover, the plan panel and divider drags hide the docked window without closing it. Turning the setting off moves the same running Chrome (same process and pages) to a normal external window; turning it on docks it again. **Headless browser** applies to the next browser launch only: a running browser keeps its mode, and headless browsers never create a pane or window. The pane has no additional app-owned header or close button; use Chrome's normal tab/window close controls. Closing Chrome leaves OMP running, and a later `browser.open` reuses the retained profile.
- **Browser** (full-session toolbar, not the global toolbar) shows that terminal's own browser next to its terminal, whatever the global *Show browser inside app* setting says: it starts the isolated Chrome headed if it is not running, or docks the already-running headed one (same process, same tabs; nothing is navigated). Other terminals and the global settings are unchanged. If the running browser is **headless**, the button asks before restarting it, because its open tabs are lost; declining changes nothing. Changing any Browser setting afterwards returns every terminal to the global preference (running browsers are not restarted). The button is disabled while the terminal is stopped; it never prompts a model.
- Tabs you open by hand in a browser started with the **Browser** button are visible to the agent on its first `browser.tabs()` / `browser.tab(name)`, even before it has called `browser.open` (they are attached as `tab-1`, `tab-2`, …). Asking for tabs never starts a browser.
- Closing the last normal tab/window also retires that terminal's owned Chrome background process, even when Chromium keeps its no-startup-window connection alive. A later Browser click or native `browser.open` starts a fresh window using the same retained cookies/profile; concurrent page creation is serialized with this retirement.

### The Manager

- Click **The Manager** to open/reopen its saved native OMP session. Missing singleton definitions are provisioned without forcing a folder chooser.
- Every ordinary agent's path, and the Manager's and Architect's, is a **Change working directory** button in its session, card and tree row (helper and plan agents show plain text). Browsing starts at the effective directory; cancellation changes nothing. Queued changes show Pending/Applying and keep the old effective path until acknowledgement; the move happens at the next safe agent step and keeps the session. Only you can change it: neither the Manager nor any model can. Changing an owned worker's folder does not move its Manager; the next handover or return recomputes the Manager's folder.
- Ask it to use **manage_sessions** to create dashboard workers, review their code/execution, inspect native plans, and handle native questions/approvals. Workers appear as ordinary dashboard instances, not OMP subagents.
- Existing user instances are independent until you click **Hand over to The Manager**. With **exactly one** connected ordinary agent (subagents, helpers and plan agents never count; stopped workers do) the Manager moves itself to that agent's own working directory and the agent stays where it is. With more than one, the Manager moves to their common repository ancestor, or to its neutral app workspace when they share none. That computed shared folder is remembered by the app and never offered in the **Previous projects** drop-downs of Dependency tree or Code quality unless it is also a real project folder you opened or chose. **Take back control** immediately revokes controller access without restarting the worker.
- **Needs you** shows an intervention reason. Open the worker and handle its native prompt, or press **Return to The Manager** after supplying the missing context. The Manager cannot clear its own human-intervention gate.
- **Settings → Show Manager tile** hides only the overview/tree row. The toolbar button, startup target, and session switcher remain available; notifications continue with the tile hidden or previews off.
- Stopping The Manager leaves workers running. Completion/decision notifications queue while it is offline and replay when it reconnects. Queues last only for the desktop app's lifetime; native OMP history remains durable.

Example: “Use manage_sessions to create a worker named API in C:/projects/api, ask it to review the failing build, and report when it finishes. Inspect its work before approving further execution.”

`manage_sessions` takes strict **flat** arguments, never `payload` or nested `config`: for example, `{"action":"create","name":"API","projectPath":"C:/projects/api","start":false}`, then `{"action":"screen","instanceId":"<worker-id>"}` or `{"action":"send","instanceId":"<worker-id>","message":"Review the failing build","delivery":"follow_up"}`. Every action except `list` and `create` requires the explicit worker `instanceId`; native keys/answers also require the generation and decision identity returned by that worker. Explicit `false` settings are retained. Intent metadata is supplied and removed by OMP itself, not part of the application tool arguments.

### The Architect and the Dependency tree

- **The Architect** (immediately left of **The Manager**) is one ordinary OMP agent, not a manager: it has no `manage_sessions` and cannot own sessions. It is provisioned alongside Manager without starting a process; clicking it opens/reopens its saved session. Its full-screen toolbar has **Dependency tree**, **System overview** and **Code quality**.
- **Give repo to architect** on an ordinary worker supplies only its saved repository path to Architect. It does not read the worker's prompt/screen/transcript, transfer ownership, interrupt work, start a stopped Architect or navigate away. Pending/Applied/failed status remains visible beside the action and Architect path.
- The next explicit Dependency tree, System overview or Code quality entry uses Architect's committed real directory once; temporary coordinator workspaces defer to each analyzer's saved manual folder/shared history. Background directory updates never replace an already open analyzer's selection or start a scan. Architect's analyzer-entry buttons are disabled while its directory change is Pending/Applying; independent analyzer browsing remains available.
- **Dependency tree** is its own page (**Back to The Architect** returns). Choose a project folder (the folders of your saved sessions, or **Browse…**), then **Direct dependencies** (the project and what it declares) or **Transitive dependencies** (everything the scan reached). In Transitive mode, **Layers** limits the view to packages at most *n* steps from the project: **All** is first and the default, followed by 1, 2, 3…; direct dependencies are layer 1 and shared packages use their shortest surviving path. **Graph view** draws Sigma.js + Graphology (ForceAtlas2 layout); **List view** ranks the same filtered packages by GitHub stars ascending, then contributors ascending, with unknown values last and 50 rows per page. Choices are remembered.
- The app scans manifests and local installs itself, executing nothing and downloading nothing: npm (`package.json` + `node_modules`, pnpm layouts included), PyPI (`pyproject.toml`, `requirements*.txt` + `.venv`/`venv`/`env`), Maven/Gradle (`pom.xml` including `<modules>`, `build.gradle(.kts)` string dependencies; transitive edges come from POMs in `~/.m2` and `~/.gradle` caches, parent POMs are not followed) and Cargo (`Cargo.toml` + `Cargo.lock`). The folder and its immediate sub-folders are scanned. Without `node_modules`, a virtual environment or a lock file only direct dependencies are shown, with a note.
- **Ask Architect (no manifest).** When the scan fails *only* because the folder has no recognised manifest (a typed check; permission errors, missing folders and every other failure keep their plain error text), the error line gains an **Ask Architect** button. It is only ever started by a click, never on mount or by polling. The existing Architect reads the repository through its request-bound, read-only `repo_evidence` tool (list/read only the folder of that request, at most 200 entries and 64 KiB per read; no links, no `.git`, `node_modules`, build output, `.env*` except `*.example`/`*.sample`, `*.pem`/`*.key`/`id_*`; nothing is executed) and saves a list through `submit_dependency_discovery` under `<app-config>/project-insight/<request id>/` (`request.json` with the folder key, evidence inventory hashes and the Architect launch/session binding; `result.json`; `terminal.json`). The saved list is a sourced model report, never a verified graph: items carry the declared version (never a resolved one), a relationship and citations (`path[:line]` shown *unverified* unless the cited path exists in the repository), and it is never fed into the dependency graph. Saved work is reused and unfinished or uncertain-delivery work is joined, never resent; **Run again** is the only way to replace a finished or failed request. **Create manifest…** previews a `requirements.txt` (pypi, `name==version` or `name`) or a minimal private `package.json` (npm) for the repository root; confirming writes it only if the file does not exist (exclusive creation, never overwritten, confirmation expires after 10 minutes) and rescans. Other ecosystems keep the list: *Manifest creation is not supported for <ecosystem>; the list remains available here.* The same request infrastructure (kind `requirements`, tool `submit_requirements_findings`) fills gaps in **Project requirements** with Architect findings that are always labelled unverified and never change the app's own detected/install states.
- **Package language selector.** When the scan contains more than one package ecosystem (for example npm and PyPI) a **Language** menu (*All package languages*, then one entry per present ecosystem) appears next to the view menu. The choice is applied once, before every view filter, so the graph, the list, its counts, the search index and metadata loading all use only that language; edges between ecosystems are dropped, none are invented, and **Show all** never shows another language. A choice that is no longer present resets to all; a single-language project shows no menu.
- **Project requirements** (Dependency tree toolbar, available even when no manifest was found) lists what the selected repository itself declares it needs, grouped as runtimes, build tools, package managers, container engines, OS features, system settings and executables/scripts. Each row shows *need* (required/optional/unknown), where it runs (this computer, WSL, container), whether it was *found/not found/unknown* here, and whether OMP Manager can install it; click a row for the explanation, file evidence (path and line), environment and install note. Static analysis reads the project root and its immediate non-hidden sub-folders with the same ignore-filtered, link-free enumeration Code quality snapshots use (bounded depth/count; `.env*` except `*.example`/`*.sample`, keys, certificates, `.npmrc` and similar secret-looking files are never read or cited; evidence lines that look like they carry a credential are replaced): `Cargo.toml`/`rust-toolchain*`/`tauri.conf.json`, `package.json` (`engines`, `packageManager`, lockfiles, `bin`, script names), `pyproject.toml`/`requirements*.txt`/`.python-version`, Maven/Gradle files and wrappers, `global.json`/.NET projects, `.nvmrc`, Dockerfile/compose files (base images), `.gitmodules`, executables (`*.exe|bat|cmd|ps1|sh`, `gradlew`, `mvnw`) in the root, `bin/` and `scripts/` with the file that references them, and README/`docs/` lines that mention `podman`, `docker`, `wsl`, `winget`, `vm.max_map_count` or `fs.file-max` (need *unknown*: documentation is not proof). Project scripts are listed, never run. Detection locates only the fixed allowlist `cargo, rustc, node, npm, pnpm, yarn, python, pip, java, mvn, gradle, dotnet, docker, podman, wsl, git, bun` and runs `--version` with a 5-second limit and no shell; a failed or timed-out check is **unknown**, never *not found*, and a container engine is only called *not found* when no client and no installed runtime was seen and no WSL distribution could be hiding Docker. Container engine, WSL and winget rows use the same read-only prerequisite probe as Code quality's *Recheck*; no engine, Podman machine, WSL distribution or installer is ever started by opening this view or a row. The two Code quality system settings (`vm.max_map_count >= 524288`, `fs.file-max >= 131072`) are always listed, labelled as required by Code quality analysis rather than by the project. Install availability is fixed: Podman, Docker Desktop/Docker in WSL, the WSL Windows features and those VM limits are *Installable via Code quality setup* (Windows only; **Open Code quality setup** in the row popup navigates there and installs nothing by itself); every other tool is *Manual install* (`No installer in OMP Manager.`). **Ask Architect to fill gaps** (only on click) asks the Architect to read the repository and lists its findings separately under **Architect findings (unverified)**, with citations; they never change a detected state above.
- **Classify with The Architect** sends the direct packages not yet judged (at most 600 per request) to the Architect, which marks each *basic* (built in: framework core, runtime foundations, type definitions) or *chosen* through its `classify_dependencies` tool; answers are saved under `<app-config>/architect/classifications/`. Basic packages, and packages reachable only through them, are hidden until **Show all** is on. Unclassified packages are always shown.
- **Package insights.** Hover or click a package (non-root) for the versions the project actually uses (installed/locked evidence), the declared ranges, the official registry's newest/recommended release, GitHub stars, linked-account contributor count and owner type, and official download counts with their period (npm: last 30 available days; crates.io: last 90 days; PyPI and Maven Central: unavailable). Contributor count and owner type are public proxies, not a verified maintainer count or proof of a professional team. A package is drawn **red** when any resolved project version is at least two numeric major versions behind the registry's newest release (for example used 3.x, newest 5.x; 4.x against 5.x is not red). Declared ranges, unsupported version formats and missing metadata are never guessed; red is version age, not a security finding. Lookups send only package names to npm, PyPI, crates.io, Maven Central and GitHub, are cached under `<app-config>/package-insights/`, honour provider rate limits, and are labelled partial when incomplete. GitHub requests are authenticated (token sent only to api.github.com) with `GITHUB_TOKEN`, else `GH_TOKEN` (the process environment, on Windows also the current user environment), else the token of an installed, logged-in GitHub CLI (`gh auth token`, also found in its usual install folders when the app's `PATH` is stale). A missing credential is looked for again every 30 seconds, when the window regains focus and on **Recheck GitHub login**; the GitHub budget line names the reason when requests are anonymous (CLI not found, not logged in — run `gh auth login` —, unusable value, or a token GitHub rejected with 401, which is retried once anonymously). Switching between anonymous and authenticated use discards the saved budget and cooldown.
- **Security review.** Ctrl+click (or Cmd+click) a package, or press **Security review**, to ask the existing Architect, never The Manager, to investigate security fixes from each resolved version to the newest release across every intervening major release. The Architect submits a sourced report through its `submit_dependency_security_review` tool (saved under `<app-config>/architect/security/<request id>/`) and it appears in a closeable dialog. It is a model-written, sourced report, not an independent vulnerability verdict; no findings is not a clean bill of health, and nothing is installed or upgraded. Each finding also carries a **project applicability** judgement (relevant, not relevant, unknown) with the reasoning, preconditions and project-relative file/line citations; not-relevant needs positive source evidence and unknown is never presented as safe.
- **Saved analyses are reused.** The latest request per package and kind (security or usage) is kept on disk, completed ones included: reopening, navigating away, or restarting the app returns the same saved result, or joins the work still in flight, and sends no new prompt or metadata request. **Run new review** is the only way to replace a completed or failed analysis. Dialogs show the versions and registry release the saved review was made for separately from today's scan, plus its date and dependency-context id. Each request is bound to the Architect launch (a hash of its private bridge token) and native session; if that session is stopped, switched or replaced before it answers, the request becomes an explicit `producerEnded` error (marker `terminal.json`) and only a deliberate rerun replaces it. Reports from earlier versions stay readable with applicability *unknown*.
- **Explain how this package is used** asks the Architect (through `submit_dependency_usage_explanation`) what concrete capability the package gives this project, tracing transitive chains to a feature or build/test function with local source citations; a package with no established use is reported as not observed or unknown, never as removable. Finished security and usage results are also printed in full in the Architect console, display-only: they are queued and printed only after the session is idle with nothing pending, never as a prompt, steering message or follow-up, and terminal control characters are shown as visible text. Reopening a saved result from the dependency tree replays that text (labelled *Saved analysis — not rerun*) without starting an analysis.
- **Dependency context for the Architect.** Every dependency scan saves the complete scanned graph (every direct and transitive package with its versions, project/known-standard/in-house judgements and saved package metadata, plus every `package -> dependency` edge) as an immutable, project-bound snapshot under `<app-config>/architect/dependency-context/<sha256>/` (`summary.json`, `packages.jsonl`, `edges.jsonl`). Saved metadata is read from the cache only: publishing never contacts a registry, resolves a token or runs `gh`. The Architect reads it through its read-only `inspect_dependency_context` tool (sections summary, packages, edges, package, work; paged, output capped at 256 KiB); a request id resolves only an app-owned request bound to the current Architect launch and session. Analysis prompts carry the context id, and packages marked in-house are never to be looked up publicly while the privacy gate excludes them.
- **Full project security review.** The toolbar button reviews every **direct** dependency of the scanned project, including hidden built-in ones and independent of the Direct/Transitive/Layers/path/List view, and consults transitive packages only where relevant to a finding. It reuses each package's latest saved or in-flight security review and sends ONE Architect prompt for the packages that need new work (none when everything is already saved). With the privacy gate on, an incomplete in-house sweep blocks the whole review and marked in-house packages are listed as skipped instead of being looked up. When every child review is terminal the app compiles the aggregate (counts, findings per package, explicit failed/skipped coverage and limitations) locally from the saved reports; no summary model call exists and the result is saved under `<app-config>/architect/project-security/<request id>/`. Only **Run new project review** replaces a finished project result.
- **Dependency update plan.** A completed package or full-project security review offers **Create update plan**. The Architect drafts a plan only (it never installs, upgrades or edits project files) and saves it through `submit_dependency_update_plan` as an immutable proposal under `<app-config>/architect/dependency-update-plans/<request id>/`. Drafts are bound to the producing Architect launch/session; existing drafts are reused unless explicitly regenerated. **Hand over to The Manager** confirms the immutable revision, canonical repository list, destination working directory and whether Manager must start. Confirmation durably claims that revision, then shows **Pending** while its workspace transition waits for a safe native boundary; it does not abort an active Manager tool. Delivery uses the post-move native identity and records **Attempting** before prompt admission. A revision is delivered at most once: a restarted Pending handoff is known-unsent, while an interrupted Attempting handoff is uncertain and never resent automatically. Workers and native approval settings are unchanged.

### System overview and Repository structure

- **System overview** (The Architect's full-screen toolbar, also in the Architect session embedded in Agent setup) is its own page (**Back to The Architect** returns): the project folder (the same saved-session/shared-history drop-down and **Browse…** as Dependency tree and Code quality; computed or temporary coordinator workspaces are never offered unless they are real projects you opened), the tabs **Helicopter**, **System**, **Files** and **Functions** (System is the default), **Refresh index**, **Repository structure**, **SRS documentation** and project-conditional **Graphify**. Opening it moves no agent's working directory, hands over no repository and sends no prompt. Folder, tab, search, filters, camera, selection and back stack are kept by the app, so they survive leaving and returning.
- **Local source index, on demand.** Opening the page loads the saved index for the folder and only compares file metadata; with no saved index it builds one once. **Refresh index** is the only other way it is rebuilt (**Cancel indexing** stops a running job; starting while a job for that folder runs joins it; at most four jobs run at once). There is no file watcher, and no agent, model or network is involved in indexing, searching or expanding. The badge *Files changed since this index (metadata); possibly stale* is a metadata comparison only: only a full refresh re-reads content. A failed or cancelled refresh keeps the last complete index shown with its timestamp; a partial index (if the attempt produced one) is opened only with **View partial index** and never replaces the complete one. A missing folder or permission error is shown, and an empty repository shows an empty inventory.
- **Snapshot, limits and storage.** An index is built from an immutable, app-owned copy of the admitted files under `<app-config>/system-overview/<repo key>/<snapshot id>/` (`status.json`, `inventory.json`, `index.json`, `source/`), never inside the repository. Inventory uses Code quality's ignore-aware, link/junction-refusing enumeration at full depth (honours `.gitignore`; skips `.git`, `node_modules`, build output and links/junctions; the secret-looking-file exclusions of `repo_evidence`; documentation and configuration files are included): at most 100,000 files / 1 GiB. Every admitted file is copied and hashed (SHA-256 of its complete bytes), and a file that changes while being copied fails the attempt instead of mixing versions. Paths keep their exact case and Unicode; paths that differ only by case are reported as a conflict, never merged. The parser admits files up to 2 MiB and 2 million syntax nodes each, with a 5-second hard timeout per file (the parser child is killed and restarted, the file is marked failed) and a 15-minute deadline per job; serialized facts are capped at 128 MiB, and reaching the cap marks the coverage partial and names the last fully processed file. Binary, oversized, unsupported, partial or failed files stay in the inventory and in coverage. Nothing from the repository is executed, built or resolved outside the snapshot.
- **Parser runtime.** Functions and call sites come from Tree-sitter grammars driven by an app-owned Python worker (`bridge/source-index/`, materialized by the app and run as `python -I -B` from an app-owned directory; no repository module name is ever imported). Only a fixed allowlist of 24 `tree_sitter_*` grammar packages is accepted (baseline Tree-sitter 0.25.2). The interpreter is `OMP_SYSTEM_OVERVIEW_PYTHON` when set; otherwise on Windows the Graphify environment, `%LOCALAPPDATA%/Graphify/venv/Scripts/python.exe` (only its grammar packages are used, not Graphify's own graph extraction), elsewhere `python3` on `PATH`. The app never installs or updates packages. A missing or incompatible runtime/grammar shows a notice that names the override, records per-language availability, and leaves the inventory and Repository structure usable. This is a local parser, not an OS sandbox: it runs with your user rights.
- **Languages.** Frozen, exact-case extension profiles (never repository plugins): Python; JavaScript/JSX; TypeScript/TSX; Go; Rust; Java; Groovy/Gradle; C; C++ (including CUDA/Metal); Ruby; C#; Kotlin; Scala; PHP; Lua; Swift; Bash; PowerShell; Zig; Elixir; Objective-C; Julia; Fortran; Verilog/SystemVerilog. `.svelte`, `.vue`, `.astro` and `.ejs` files keep independent embedded-script regions with their original byte offsets; templates and styles are separate coverage, not parsed as functions. Any other file is inventoried but gets no invented functions.
- **Facts and resolution.** Every declaration (named, nested, anonymous, methods, constructors), import/include/module/export and recognized call or reference site is stored with its exact path and source span; ids hash path, language, region, kind and span, so same-named functions and case or punctuation variants stay distinct, and isolated or recursive functions are kept. A separate pass over the whole inventory labels each site: `resolvedStatic` (a lexical binding with no conflicting rebinding, or a literal file/module target under the language's rules, for example relative JS/TS imports with tsconfig paths and package exports, Python imports inside the snapshot, Rust crate/mod/use trees, literal C/C++ includes), `candidate` (conditions, several possibilities, overloads or name-only matches; labelled candidate even when only one exists), `dynamic` (dynamic receivers, callbacks, reflection, shell commands, macros), `external`, `unresolved` or `unsupported`. A shared name, path proximity or a test/non-test preference never promotes a site. Every recognized site is kept even with no target.
- **Coverage is explicit.** A coverage panel lists admitted, parsed, partial, failed and skipped files, encountered/resolved/unresolved/dynamic sites, per-language rows, exclusions and warnings. Unsupported, partial or failed files are inspectable entries, never proof of zero connections, and no root or reachability edge is invented to make an isolated function visible.
- **System / Files / Functions.** **System** starts as one application box with *No generated system diagram yet*: inventory alone is not a system map. **Files** shows the full admitted inventory (isolated files included), explicit import/include/module/re-export edges and, labelled separately, cross-file aggregates derived from function calls. **Functions** shows every indexed declaration, filterable by relationship and resolution, with callsites that have no target listed beside the graph; selecting a function shows its callers, callees and source spans. A group drills System to Files to Functions with **Back**, selecting a card or arrow opens the callsites or config citations behind it, and search covers the complete index even when the view is aggregated. Strongly connected components are collapsed and layered input to application to output; containment is drawn separately from dependency arrows (group membership is not a call). Arrows point from caller or requester to target; dashed means not statically proven, or a response (a response is never a new caller).
- **Renderer choice.** Views of at most 200 visible nodes and 500 visible edges use Svelte Flow (the package the Git tree uses). Larger Files/Functions views use Sigma.js + Graphology with a ForceAtlas2 layout computed in a cancellable web worker, up to 5,000 nodes / 20,000 displayed edges; beyond that the view groups by directory and says so. The page always shows displayed against total nodes and relationships, with relationships hidden by filters or inside groups accounted for, and the exact neighbourhood of any search hit can be opened. Labels are plain escaped text.
- **Generate system diagram** asks the existing Architect, only on click (never on open, refresh, search or expansion). The request (kind `systemOverview` under `<app-config>/project-insight/<request id>/`, with `index-ref.json`) binds the repository, the exact index snapshot and hash and the Architect's launch/session, and follows the same saved-result, producer-bound and never-resend-uncertain-delivery rules as the other Architect analyses. The Architect reads only that immutable snapshot, not the live folder, through the request-bound `repo_evidence` and `system_overview_inspect` tools and saves through `submit_system_overview`. The result is labelled **Architect analysis**: cards (application, logic group, actor, service, sidecar, cache, database, queue, storage, external, entrypoint), relationships (calls, imports, includes, reexports, references, renders, requests, responds, publishes, subscribes, reads, writes, authorizes), evidence (path, line range, content hash, each checked against the snapshot) and coverage rows (inspected, notFound, unresolved, excluded) with limitations. A relationship is **declared** only when it names an indexed declaration or resolved static edge; otherwise it is **inferred** or **unknown**, and a path that merely exists or prose never makes it declared. It describes what source and configuration say, not verified runtime traffic, live deployment or every possible connection; the Architect is asked to cover every inventoried area or mark it unresolved or excluded, and nothing is started, built or scanned. Credentials, raw URLs and secret contents are rejected from labels. Invalid, dangling, duplicate, oversized (2,000 cards / 5,000 relationships / 2,000 evidence records) or wrongly bound results are rejected with an error, never trimmed. Saved results open passively with a revision selector; **Regenerate** creates a new immutable request, **Discuss in The Architect** shows a saved result in its conversation, and a diagram made from an older index is marked.
- **Analysis-only turns.** App-created visualization prompts use a human-only native control: the prompt is queued as a follow-up with template/command expansion disabled and carries a one-time nonce. While the turn carrying that nonce runs, only `repo_evidence`, `system_overview_inspect`, `read_target_structure`, the matching submit tool and native Ask are allowed; execution, edits and delegation are refused, and a saved result ends the generation. Unrelated Architect turns and work already running are not restricted; this guards that turn only and is not isolation from other agents.
- **Repository structure** (page header; a separate work area, not a fourth diagram level) shows a generalized, collapsible current tree from the complete inventory immediately; repeated component/feature patterns collapse into labelled groups whose exact members stay expandable, so no path is lost. **Analyze current structure & naming** asks the Architect (kind `structureCurrent`) for group purposes and evidence-based naming conventions; **Preview target structure** (kind `structureProposed`) draws the target separately, with its source document's identity (type, capture time, SHA-256, size, excerpt) above it; **Approve preview & discuss** and **Discuss with Architect** are described below. A disabled action lists its reason beneath the buttons.
- **The pasted Markdown is the only authority.** You paste the target structure into the native Architect chat. A passive listener in the Architect's main interactive session records eligible submissions (a heading, a fenced structure/tree, or a long paste saved by OMP as a local paste file); it never consumes or rewrites your message and starts no model turn. App prompts, RPC/extension input, model output and tool arguments can never create a source. The captured text is what the native editor submitted (after paste expansion, before template/mention expansion), not a claim about original keystroke bytes; for a pasted-file reference the file's body is read through the SDK's own local-URL mapping, not the URI. A source is at most 1 MiB of valid UTF-8 without links; unusable submissions appear with the reason instead of being truncated. The newest 20 bounded submissions are kept in memory for **Use last submitted message**; at most 20 sources / 20 MiB per native session are saved under `<app-config>/architect/structure-sources/<session id>/`. **Target Markdown source** lists time, type, excerpt, size and SHA-256, shows the read-only text, and **Use this Markdown** selects it before **Preview target structure**; with none it says **Paste the target Markdown in Architect chat first** and offers **Open Architect** (no prompt sent). Earlier messages, or another session's, are never guessed: paste again.
- **Preview, conflicts and revisions.** A preview request copies the selected Markdown's immutable bytes (hash re-checked) into the request as `target.md`; the Architect reads exactly that through `read_target_structure` and submits through `submit_repository_structure`: tree entries, current and proposed naming conventions, mappings (unchanged, rename, move, split, merge, create, remove), conflicts and evidence. Proposed destinations must be clean, collision-free relative paths (Windows case collisions are rejected); splits and merges are explicit, never invented one-to-one. A model may flag **Target document conflicts** and propose a labelled adjustment; it cannot change the source or call a conflicting proposal compliant. Regenerating creates a new immutable revision with an explicit predecessor, choosing a different document starts a new lineage, and badges mark *Index changed since this analysis*, *From a different document* and *Replaced by a newer preview*; a late older result never replaces a newer selection, and a changed session or generation rejects the selection rather than substituting another.
- **Approval is discussion only.** **Approve preview & discuss** is enabled only for the selected, completed, unsuperseded proposed revision; its dialog shows the request id, result hash, source id/hash, any conflicts and the target Markdown, which must have been read first. Approving records a selection marker, not an implementation authorization, and conflicts do not block it: the preview is approved with *Target document conflicts* retained, and the Markdown is never fixed automatically. The producing Architect then receives one message naming the preview and the hashes, saying the Markdown remains the source of truth and the diagram an aid, that the selection does not authorize repository edits, execution or restructuring, and that any conflict is discussed before a later implementation instruction. Delivery uses a durable claim: it is made at most once, an interrupted or unknown delivery is shown as uncertain and never resent automatically, and if the producing session was stopped or replaced the approval is kept and **Open Architect** offers the discussion in the current session without binding the old source to the new one. **Discuss with Architect** replays the chosen analysis and source identifiers in the same conversation without approving. Moving or renaming files is a later, explicit instruction you give the Architect, under its normal permissions; no file-moving engine or Manager handoff exists here.
- **Switching to the Architect and back.** **Generate system diagram**, **Analyze current structure & naming** and **Preview target structure** admit or join the request and then focus the existing Architect so you can watch. If the backend refuses before anything is sent you stay in the overview with the error; unconfirmed delivery shows as waiting and is never resent. The app, not the page, watches that exact request by id and returns to the matching System or Structure view only when that typed result is saved, that Architect's turn is quiescent (idle, nothing pending), you are still looking at the Architect this click opened, and the request, producer and selected source still match. Manual navigation (including opening the native Agent Hub), a project switch, selecting another source, Back, another generation or a replaced session cancels the automatic return; a result that arrives afterwards shows an **Open System overview result** button in the global toolbar instead of taking the screen. An unrelated completion or older revision never triggers a return. After ten minutes the page reports it is still waiting and offers **Check again**; background work is not cancelled. Saved results, source previews and the current inventory open passively and never start the Architect or a model turn.

- **Publication guarantees.** Vault and Agent setup writes use create-only renames and a private recovery journal under `<app-config>/knowledge/`. A replacement locks the note, verifies its hash, saves the original privately, moves it aside and renames the new note in; no step overwrites anything. If another program creates the note during the brief empty-name window, that note wins, nothing is lost, and the error names the private backup. Each rename is atomic but a replacement is not continuous-name atomic, and publication is Windows-only (other platforms refuse rather than write unsafely). Interrupted publications are rolled back at the next start without undoing a later external edit.
- **SRS ledger guarantees.** Completion requires every reviewed capability or scenario to map to a stable requirement (or an evidence-backed N/A or an authenticated human exclusion); saved stakeholder answers are available to resumed stages through question inspection; document reviews bind exact work revisions and go stale lazily without a total dependent-document cap; interrupted inventories reconstruct counters and links before generation resumes; public filenames such as `orders.json` are allowed while private source paths, symbols and citations stay out of published notes.

### Helicopter, knowledge vaults, Graphify, Cognee and SRS documentation

- **Helicopter** is the leftmost System overview tab (order **Helicopter / System / Files / Functions**; System remains the default). It is a plain-language business picture for non-programmers: who uses the product, what starts each journey, the steps and decisions, outcomes and outside parties, plus every business capability the Architect identified. Nothing is generated on open; **Generate Helicopter view**, **Regenerate**, the revision selector and **Discuss with Architect** use the same snapshot, ticket and navigation rules as System. It is generated by the one existing Architect in the same native conversation as the System view, in either order (`submit_helicopter`, kind `helicopter`); no second agent, context-transfer layer or model client exists. Uncertain steps are labelled **Needs clarification**; technical evidence is shown only on request.
- **Vaults.** One Markdown vault per project and one global vault are registered only by you (`prepare_knowledge_vault` then `confirm_knowledge_vault`; default offers `<repository>/Knowledge` and `<home>/OMP Knowledge/Global`). Existing Obsidian vaults are never adopted silently; unrelated notes are preserved, home/drive roots, `.omp`, app-config, credential/session/package folders, links and overlapping roots are refused. Vaults hold app-authored Markdown only: no tools, scripts, plugins or configuration. Bindings, indexes, journals and baselines live under `<app-config>/knowledge/`, never in a vault. Obsidian is detected passively (never launched, no CLI, no registry or settings edits); **Open in Obsidian** builds an `obsidian://open?path=` link and launches the installed app separately from OMP Manager, or shows **Open vault manager** when the folder is not registered in Obsidian. Without Obsidian, **Install Obsidian** only opens the download page; declining keeps plain Markdown mode (**Documents view**).
- **Vault viewer.** One in-app split view (file menu, rendered Markdown, note graph) serves Agent setup and SRS results. Markdown is rendered with raw HTML disabled and sanitized output; wiki links, aliases, heading/block references and transclusions are supported, scripts/HTML/Mermaid/Dataview/plugins never run and remote images are not fetched. Documents page in 64 KiB exact-UTF-8 pieces with no total size limit. Note relationships are drawn undirected; only Source/System/Helicopter/Graphify directed records have arrowheads.
- **Agent setup vault.** Enabling a target (Global, Manager, Architect, Local AI models, repository, named profile) is a reviewed **Import Markdown** of native instruction/rule/skill/workflow Markdown only. Local AI models uses the global vault namespace `Agent setup/Local AI models`. Edits in the vault are inactive until a reviewed **Apply to OMP** (diff, ten-minute single-use token, native drift needs re-import, explicit deletions, journaled atomic per-file renames with immutable backups under `<app-config>/knowledge/deployments/`, held native sessions, recovery before any app-managed instruction load). Tools, scripts, plugin modules, package/config files, credentials and sessions stay native and are never copied. A deployed batch is recoverable but not externally atomic: standalone OMP can observe an intermediate batch.
- **Graphify** is reachable from System overview for any selected project. A valid local output (`graphify-out/graph.json` with a matching `.graphify_root`, or labelled **Unverified** without one) or a human-registered external output whose `.graphify_root` names the project opens an immutable app-owned snapshot (full hash) in a read-only graph with provenance (EXTRACTED/INFERRED/AMBIGUOUS), multigraph edges, self-loops, communities and hyperedges. Otherwise a dialog shows what was found (absent, foreign with the claimed root, malformed, unreadable) and offers **Choose existing Graphify output…** (native folder picker; accepted only when its marker names this project; cancel changes nothing). Copies of a workspace are never adopted by name and markers are never edited; Graphify is never run and repository `graph.html` is never opened. A replaced live output shows **New Graphify output available — Refresh** while the old snapshot stays readable.
- **Cognee** appears in the System overview header only when an installation is found passively; there is no global Cognee button and nothing to configure. Passive discovery reads installation metadata without executing Node; Node's version is checked only on explicit **Open Cognee UI**. Open revalidates the installed `cognee-frontend` (exact Next.js 16.3.4 development layout, Node.js, TypeScript/React/Node typings, and the matching installed native SWC binding: Windows x64/arm64, Linux GNU x64/arm64, or Darwin x64/arm64) and an already running local Cognee backend (installed-venv `python -m uvicorn cognee.api.client:app`, including `venv/bin/python` on Unix, owning a loopback listener with matching process-creation identity; port 8000 preferred). It starts only this app's frontend, `node next dev --turbopack --hostname localhost --port 3000`, checks that `/api/runtime-config` names that backend and opens `http://localhost:3000`. The frontend is owned by a Windows Job Object or a dedicated Unix process session retired on stop/exit; process ownership is not a sandbox. The app never installs or downloads a frontend or dependencies, starts the backend, MCP or Docker, runs migrations or touches Cognee's stores; a missing component is reported with nothing spawned, a foreign listener on port 3000 is left alone, and only the frontend this app started is stopped. ### Code diff

- **Code diff** (full-session toolbar) opens a page for that session's project: a sidebar lists every changed file and a drop-down above it selects the baseline - **Since last commit** (`HEAD` against the working tree, including staged, unstaged and untracked files) or **Compared with master** (the branch tip against the working tree). The comparison branch is `master` when it exists, otherwise the repository's recorded default branch (remote HEAD or `init.defaultBranch`), otherwise `main`; the real name is shown and nothing is fetched. It works for stopped sessions and The Manager.
- The selected file opens in a bundled Monaco editor (the editor component of VS Code, loaded locally, no network): side-by-side diff with line numbers, the baseline side read-only and the working-tree side editable by typing and clicking. **Save** or Ctrl+S writes the file; nothing is autosaved and saving never stages anything. Saving preserves a file's BOM and LF/CRLF endings, and a deleted file can be recreated by editing its empty side.
- Saves compare the file's SHA-256 with the one loaded and refuse to overwrite a file an agent changed meanwhile (`diff_conflict`), keeping your typed text; **Reload from disk** discards it only after you confirm. Binary, non-UTF-8, mixed or lone-CR line-ending, links/junctions, submodules and files over 2 MiB are shown read-only with the reason. Only paths in the current comparison can be read or written, never `.git`, links or paths leaving the repository.

Git is only asked questions in the other two baselines (no shell, no textconv or external diff) and must be installed.

Pressing either again for an unchanged change set shows the existing conversation instead of sending a new request. The editor stays mounted behind the agent, so unsaved edits survive; clicking a file returns to the diff. Helper agents are separate OMP sessions (same profile, config and model as the project's agent, one per project and purpose) hidden from the dashboard and the session switcher. They run with `--no-tools` and two bridge tools: `repo_inspect` (changes, log, show, diff, blame, file), which only runs fixed, validated read-only `git` commands, and the read-only saved-results reader `code_quality_report` (see Code quality), so they cannot edit, stage, commit, scan or run anything.
- The file list is a folder tree (folders collapse; collapse state lasts while the page is open) in every baseline. **Uncommitted changes** is the comparison option with index actions and mirrors VS Code's source control: **Staged Changes** (HEAD against the index, read-only) and **Changes** (index against the working tree, editable); a file staged and edited again appears in both. Row icons: **+** stages, **−** unstages, and the u-turn arrow reverts a Changes file (discards unstaged edits, or deletes an untracked file) after a confirmation; there are no bulk actions.
- **Commit** (message field under the drop-down; Ctrl+Enter also commits) commits only what is staged, runs the repository's hooks and reports Git's error text on failure. **Publish…** pushes the current branch (never forced; sets the upstream the first time), optionally after **Create new branch** (`git checkout -b <name>`), optionally followed by **Create pull request** (`gh pr create --fill`, which needs the GitHub CLI installed and signed in; its output or error is shown, and **Open pull request** opens the created link). Each step that already completed is listed if a later one fails.

### Git tree

Historical comparisons reuse the coloured file tree and Monaco diff editor but are read-only. **Back to Git tree** preserves graph selection and viewport.

## Data ownership

The manager stores launch definitions and their native session paths in Tauri's app-config directory (`instances.json`, identifier `dev.udvikler.omp-manager`). OMP owns sessions, chats, plans, configs, models, approvals, tools, and thinking visibility.
GUI startup/dashboard/browser preferences are stored in WebView localStorage under `omp-manager.settings`, separate from OMP config and global `browser.*` OMP settings. The existing Manager-tile preference is migrated; the Previews On/Off preference keeps its existing key.

The Rust reader consumes native OMP JSONL journals and their sibling artifact directories. It does not write OMP journals or copy them into a separate chat database. Where a transcript is needed (such as the plan agent's context) it is rendered with `omp render` using the instance's working directory, profile, and config overlays; the Subagents button opens OMP's native Agent Hub instead of rendering one. A bundled extension is loaded only into app-managed OMP processes; it reports exact native session identity, completion, and decisions, and exposes the Manager's controller tool. It is not installed into global OMP configuration.

Coordinator workspace requests are in-memory, per-coordinator FIFO intents, not optimistic edits to launch definitions. Active tools finish in their original directory; the native pre-model/idle boundary performs the acknowledged move, with settings/memory/skill/tool scope and session artifacts preserved. Stopped manual/Architect changes remain stopped, and saved conversations relocate through the native writer-lease-protected session manager. Ownership changes commit atomically with destination identity; take-back invalidates pending grants. Pending work is cancelled on shutdown/restart, while committed paths persist. Existing user shells retain their own directories. Native destination extension/template/workspace-tree reconciliation is cached/asynchronous: newly installed extensions can still require native reload or reopen.

Tile **working/idle** is an output-activity indicator, not an authoritative agent-lifecycle state. Tasks, plans, and child metadata reflect OMP's last persisted state; in-flight subagent status may lag until OMP persists an update. Streaming chat remains visible in the real terminal. PTY replay is bounded to 256 KiB; older history remains in OMP.

Pending human decisions are the running sessions' live native requests, held in memory by the app: their public request ids and your answer drafts are not persisted and do not survive a restart. System overview data is app-owned: source indexes under `<app-config>/system-overview/`, Architect system and structure requests, results, approvals and delivery claims under `<app-config>/project-insight/`, and captured target Markdown under `<app-config>/architect/structure-sources/`. None is written inside the analyzed repository.

## Safety and dependencies

- No telemetry, updater, tray/autostart service, external dashboard server, worker-to-worker messaging, or model-management logic.
- The desktop broker listens only on `127.0.0.1` at an ephemeral port while the app runs. Each child authenticates with a private per-generation capability. The manager's only external network requests are the read-only dependency metadata lookups to the fixed hosts `registry.npmjs.org`, `api.npmjs.org`, `pypi.org`, `crates.io`, `repo.maven.apache.org` and `api.github.com` (package names only, at most three redirects within the same host, 5 MiB responses). OMP can use the providers, MCP servers, and extensions configured by the user.
- The Tauri permissions beyond `core:default` are `dialog:allow-open` and `core:window:allow-destroy` (to close the window after the unsaved-edits guard). The frontend loads only bundled assets in release mode; its CSP allows same-origin and `blob:` workers and `data:` fonts for the bundled Monaco editor, nothing remote. Windows DLL search excludes the current directory and `PATH` to avoid ConPTY DLL search-path hijacking.
- Rust PTYs use pinned `portable-pty 0.9.0` from WezTerm. UUID and Windows API crates were inspected from their published source manifests. The Tauri CLI is compiled from source rather than installed as a prebuilt npm CLI package.
- The headless terminal mirror uses pinned MIT `vt100 0.16.2`, inspected with its ordinary `itoa`, `unicode-width`, and `vte` dependencies; it has no build script or binary-download hook. Rust handles terminal cursor reports even when no preview exists.
- The diff editor uses pinned `monaco-editor 0.57.0` (installed with `--ignore-scripts`) and `sha2 0.10.9` for the save-conflict hash.
- `package-lock.json` and `src-tauri/Cargo.lock` are checked in. Use `npm ci --ignore-scripts` and Cargo's `--locked` option.
- None of the direct npm dependencies has an install hook. The lockfile includes optional macOS `fsevents`, which does declare one; `--ignore-scripts` disables it. Vite's development toolchain includes upstream prebuilt Rolldown/Lightning CSS platform binaries. These are build-time dependencies, not silently downloaded application executables.
- Dependency metadata uses pinned `reqwest 0.13.5` (blocking, rustls, system proxy). Its TLS stack compiles `aws-lc-sys` from source; this Windows build was verified with the Visual Studio Build Tools C++ workload and its bundled CMake on `PATH`.
- OMP extensions are executable user configuration, not a sandbox. The manager does not weaken OMP's approval or thinking configuration.
- Human decision answers and the native Agent Hub use authenticated, main-window-only commands and the app's own bridge; the installed OMP SDK's files are never modified, and the in-memory hooks the bridge installs for them are removed when it shuts down. The Manager and models cannot answer a human-only confirmation, open the hub or select a target Markdown.
- System overview runs a local Python parser process over an app-owned copy of the repository: no network, nothing from the repository is executed, built or imported, and no package is installed. It is not an OS sandbox. An Architect-generated diagram is a model interpretation of source and configuration, never proof of runtime behaviour.

### Terminal browser implementation notes

- The docked window is Chrome's own top-level window positioned over the pane, not a `SetParent` child: a native probe showed cross-process child hosting painted Chrome and accepted page input but broke the address bar and browser shortcuts. Docking relies on a 40 ms Win32 reconcile loop (position, visibility, z-order). The pane is a placeholder; the real window can briefly lag behind very fast resizes or window drags.
- A per-app Bun helper (`omp-browser-service.mjs`, started lazily) owns the loopback scoped CDP proxy and drives Chrome processes that the Rust supervisor launches. Each named tab gets an unguessable `*.localhost` capability origin (Puppeteer discards URL paths); the proxy exposes only that tab, its frames/workers/opened pages and pages it creates, and blocks peer pages, browser-wide control and peer downloads. A guarded adapter (`omp-browser.mjs`) wraps OMP's live browser prelude callback; if OMP's internal shape changes it fails closed with `OMP Manager browser integration is incompatible with this OMP version`. Requires Bun and the installed OMP SDK; Chrome is found from `PUPPETEER_EXECUTABLE_PATH`, the installed Chrome/Chromium/Edge locations, or an already existing Puppeteer cache - nothing is downloaded (`browser_executable_missing` otherwise).
- Browser allocation and explicit tab-close requests use the authenticated Manager bridge. The hub keeps reading an authenticated bridge connection however long it is idle (a regression test sleeps past the 10 s hello deadline); if a connection ever stops being read it is closed so the bridge reconnects instead of waiting for a reply that cannot come. URL reads, tab enumeration and automation validate the existing tab directly through its capability-scoped CDP discovery endpoint, then use OMP's native CDP implementation; they do not depend on a redundant controller-validation round-trip. Closed/revoked capabilities still fail explicitly and closed named tabs are removed from OMP's list. The native integration regressions require `OMP_SDK_DIR` and `PUPPETEER_EXECUTABLE_PATH` and cover controller reply loss, closing Chrome and asking the same OMP session to reopen it, and an app restart, with real Chrome/SDK operations. Opening a tab is bounded (20 s): an unresponsive browser is closed with an explicit error so the next `browser.open` starts fresh. The helper's lifecycle trace is written to `<app-config>/terminal-browsers/browser-service.log` (overwritten per helper start).
- **Chrome ownership.** The helper never launches Chrome itself. Per Chrome it asks the Rust supervisor (private `native_request`/`native_response` stdio frames scoped by a random per-run `helperSession`) to `browser_spawn` a suspended, Job-contained process (kill-on-close, explicit inherited-handle list) under an exclusive no-sharing per-profile lease `<app-config>/terminal-browsers/<sha256(id)>/owner.lock`; Puppeteer then connects to that child's own numeric-loopback DevTools endpoint and calls `browser_ready`. Spawn, connect and initialization share one 20 s deadline; a late result is disconnected and retired, never published. Retirement is `TerminateJobObject` plus active-process accounting (5 s bound) before the lease is released, so a profile is never reused while its previous Chrome can still hold it. A rival supervisor sees `browser_profile_busy`; Chrome processes the app did not launch are never adopted or killed, profile files are never deleted, and launch-restored pages are closed over the owned connection. The helper's own trace is `browser-service.log`, the supervisor's is `browser-native.log` (both under `<app-config>/terminal-browsers/`). This is routing isolation, not an OS sandbox against arbitrary local code.
- Opt-in native proof: `OMP_BROWSER_NATIVE=1` with `PUPPETEER_EXECUTABLE_PATH` (and `OMP_SDK_DIR`/`BUN_BIN` if not discoverable) runs `cargo test --locked native_owned_browser_lifecycle`. Bridge fixtures use `bridge/fixtures/native-host.mjs`, a `taskkill`-based stand-in for the supervisor that is a harness, not a containment proof.
